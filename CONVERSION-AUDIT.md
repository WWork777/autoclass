# Conversion Audit — autoklass42.ru

Дата: 2025-09-21. Домен: `https://autoklass42.ru`.

## 0. Анализ существующей инфраструктуры (до реализации)

Backend/API в проекте не было — статический Next.js фронтенд без единой точки приёма заявок. Аналитики (GTM/GA4/Метрика) подключено не было. Поэтому:

- создан **единственный** API-роут `POST /api/leads/` — все формы сайта используют его;
- создана **единственная** система аналитики — `src/lib/analytics.js`, пушит события в `window.dataLayer` (совместимо с GTM/GA4/Метрикой — при подключении тега они начнут видеть события без переписывания кода);
- ничего из существующей рабочей функциональности (визуальный стиль, SEO-архитектура из предыдущего этапа) не переписывалось — все конверсионные элементы добавлены поверх.

## 1. Архитектура лидогенерации

```
src/lib/
  phone.js         — маска/нормализация телефона (+7 (___) ___-__-__ → +7XXXXXXXXXX)
  utm.js           — захват и персист UTM/источника на весь сеанс (sessionStorage)
  analytics.js     — track(event, payload) → window.dataLayer
  submitLead.js    — единая точка сборки объекта лида + POST /api/leads/
  useLeadForm.js   — общий хук состояний формы (idle/loading/success/error, anti-doubleclick)

src/components/leads/
  PhoneInput, ConsentCheckbox, FormSuccess, TrackOnMount
  ConsultationForm, CallbackForm, PriceLeadForm, SmartQuiz
  LeadModalContext (провайдер + модалка), LeadButton
  StickyCta, FinalCta, ExitIntent, UtmCapture

src/app/api/leads/route.js — единый эндпоинт: honeypot → rate limit → валидация →
  нормализация телефона → отправка в Telegram → ответ клиенту
```

Цены/категории/инструкторы не хардкодятся в формах — `PriceLeadForm` и `SmartQuiz` берут их из `src/lib/data.js` (`PROGRAMS`, `getProgram()`), того же источника, что и SEO-страницы категорий и `/tseny/`. Изменение цены в одном месте автоматически обновляет квиз, калькулятор цены и все страницы.

## 4. Структура лида

```js
{
  name, phone,                       // обязательные
  category, transmission,            // b|a|cb|db, МКПП|АКПП|"Пока не знаю"
  experience, desiredStart,          // из SmartQuiz
  comment,                           // из ConsultationForm
  source,                            // откуда конкретно пришла заявка (cta id / имя формы)
  landingPage, referrer,
  utm_source, utm_medium, utm_campaign, utm_content, utm_term,
  timestamp,
}
```

`landingPage` и `utm_*` фиксируются в `sessionStorage` при первом заходе (`captureUtm()` в `UtmCapture.jsx`, смонтирован в `layout.jsx`) и переживают переходы между страницами без параметров в URL — **проверено вручную**: заход с `?utm_source=yandex&utm_medium=cpc&utm_campaign=avtoshkola_b` на `/`, переход на `/tseny/` без каких-либо UTM в адресе, отправка формы — в логе сервера пришли исходные `utm_source=yandex/utm_medium=cpc/utm_campaign=avtoshkola_b` и `landingPage=/`.

## 5. Telegram / CRM

`POST /api/leads/` формирует сообщение:

```
🚗 НОВАЯ ЗАЯВКА

Имя: ...
Телефон: ...

Категория: ...
Коробка: ...
Опыт: ...
Желаемый старт: ...

Страница: ...
Источник: ...
UTM: ...
```

и отправляет через Telegram Bot API (`https://api.telegram.org/bot<TOKEN>/sendMessage`). Требуются переменные окружения `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — **в этой среде они не заданы**, что подтверждено логами (`TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID не заданы — заявка не отправлена в Telegram`). Заявка при этом не теряется — она попадает в серверный лог (`console.log`) и API возвращает `200 ok`. Перед продакшен-деплоем нужно:

1. создать Telegram-бота через @BotFather, получить токен;
2. получить `chat_id` группы/менеджера;
3. прописать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в переменных окружения хостинга.

Если позже понадобится полноценная CRM (Bitrix24/amoCRM), достаточно добавить ещё один вызов внутри того же `route.js` рядом с `sendToTelegram()` — двойной интеграции без изменения фронтенда.

## 6. Анти-спам

| Механизм | Реализация | Проверено |
|---|---|---|
| Honeypot | скрытое поле `website` в каждой форме, видно только ботам | ✅ `POST` с заполненным `website` возвращает `{ok:true}`, но не уходит в Telegram/лог |
| Rate limiting | in-memory, 5 запросов/60 сек на IP (`route.js`) | ✅ 6-й запрос подряд с одного IP → `429` |
| Серверная валидация | имя ≥2 символов, телефон приводится к `+7XXXXXXXXXX` и проверяется на 11 цифр | ✅ `phone: "123"` → `400 "Укажите корректный номер телефона"` |
| Защита от повторной отправки | `submittingRef` в `useLeadForm` блокирует повторный submit, кнопка `disabled` во время `loading` | ✅ |
| Нормализация телефона | `normalizePhone()` на клиенте и `normalizePhoneServer()` на сервере — независимая проверка | ✅ |

CAPTCHA сознательно не добавлена — honeypot + rate limit достаточны для форм такого объёма трафика, лишний шаг снизил бы конверсию без реальной необходимости.

## 7. Согласие на обработку персональных данных

Каждая форма (`ConsultationForm`, `CallbackForm`, `PriceLeadForm`, `SmartQuiz`, `FinalCta`) содержит чекбокс `ConsentCheckbox`:
- **не отмечен по умолчанию** (`useState(false)`);
- ссылки на `/privacy/` (политика обработки персональных данных) и `/documents/` (сведения об организации) — обе страницы существуют и открываются в новой вкладке;
- отправка блокируется без согласия (`if (... || !consent) return`), с явной ошибкой под чекбоксом.

## 8. UX и доступность форм

- **Маска телефона** — `+7 (___) ___-__-__`, устойчива к вставке в любом формате (`8912...`, `+7912...`, с пробелами/скобками) — протестировано программной вставкой значения `9123456789` → корректно отформатировано в `+7 (912) 345-67-89`.
- **Loading** — кнопка меняет текст («Отправляем…» / «Подбираем…») и получает `disabled`.
- **Ошибки валидации** — под полями (`aria-invalid`, `aria-describedby`, текст ошибки), не сбрасывают введённые значения — состояние полей (`useState`) не зависит от статуса запроса.
- **Success state** — компонент `FormSuccess` с `role="status"`.
- **Клавиатура/фокус** — `:focus-visible` определён глобально в `globals.css` (красный outline), инпуты не используют `outline-none` без замены на видимый focus-стиль бордера.
- **Мобильные тач-таргеты** — кнопки минимум 44px по высоте (py-3.5/py-4).

## 9. Найденный и исправленный баг

При тестировании **SmartQuiz** обнаружено: `AnimatePresence mode="wait"` с несколькими условными `{step === N && (...)}` блоками внутри одного `motion.div` приводила к рассинхронизации — прогресс-бар шагов обновлялся (state менялся корректно), но видимый контент шага не переключался (застревал на шаге 1). Найдено через прямое DOM-тестирование (клик → проверка `dataLayer` длины и текста диалога). **Исправлено**: убран `AnimatePresence`, оставлена простая анимация появления на `motion.div` с `key={step}` — после фикса пройден полный сценарий из 5 шагов с корректным отображением каждого шага и финальным результатом на основе реальных данных (`PROGRAMS`).

## 10. Проверено вручную (эта сессия)

- [x] Все страницы возвращают `200` после интеграции lead-gen (не сломана SEO-архитектура).
- [x] `POST /api/leads/` — валидные и невалидные данные, honeypot, rate limit.
- [x] UTM переживает переход между страницами без UTM в URL.
- [x] SmartQuiz — полный путь 5 шагов, персональный результат из реальных цен.
- [x] ConsultationForm на `/tseny/` — заполнение, чекбокс, отправка, success state, событие в `dataLayer`, лог на сервере с сохранённым UTM.
- [x] Аналитика — `cta_click → form_open → form_start → form_step_complete → form_submit → form_success` зафиксированы в `window.dataLayer`.
- [x] Дублирующий 308-redirect на `/api/leads` из-за `trailingSlash: true` устранён — клиент обращается сразу на `/api/leads/`.

## 11. Не проверено / ограничения (честно)

- **Telegram-доставка** — код готов и протестирован в режиме "токен не задан" (заявка не теряется, пишется в лог); реальную доставку сообщения в Telegram нужно проверить после того, как на хостинге пропишут `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`.
- **Rate limiter in-memory** — работает для одного Node-процесса. На serverless-хостинге с несколькими инстансами (Vercel Functions и т.п.) лимит будет считаться отдельно на каждый инстанс — для строгого лимита нужен внешний стор (Upstash Redis и т.п.). Для текущего объёма трафика автошколы это не критично.
- **Lighthouse/Core Web Vitals** — не прогонялся инструментально в этой сессии (см. также SEO-AUDIT.md, раздел 7). Новые клиентские компоненты (модалки, StickyCta, ExitIntent) рендерятся лениво (появляются только после взаимодействия/скролла/задержки) и не должны заметно влиять на LCP главной страницы, но замер на реальном билде не выполнялся.
- **Мобильный экран** — проверено через DOM/JS (наличие `env(safe-area-inset-bottom)`, `hidden lg:flex` для ExitIntent на mobile), но не через реальный визуальный скриншот на мобильном вьюпорте (в этой сессии инструмент скриншотов не отдавал реальные пиксели из-за сворачивания окна — см. ограничение, зафиксированное в предыдущих этапах работы).
- **CallbackForm и «задать вопрос» с отдельным полем комментария на FAQ** — компонент готов, но пока не размещён отдельной видимой кнопкой на сайте (доступен программно через `LeadButton kind="callback">`); при необходимости можно добавить, например, в шапку или в блок контактов как третий вариант связи.

## 12. Итог

Реализована единая архитектура лидогенерации поверх существующего дизайна: 4 формы под разные намерения (не универсальный popup), один API-эндпоинт, одна система аналитики, персистентные UTM, честные данные без выдуманных цен/сроков/отзывов/скидок. Найден и исправлен реальный баг в UX квиза до сдачи. Ключевое ограничение — Telegram-токен и Lighthouse-прогон нужно донастроить/проверить на реальном хостинге.
